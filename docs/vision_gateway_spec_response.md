# Vision Gateway / 최종 서버 개발 명세 검토 회신

작성일: 2026-10-01

검토 대상: `raspberry_gateway.txt`, `relay_server.txt`

상태: 서버 측 검토 의견 및 협의 요청. 기존 시스템 교체나 데이터 폐기를 승인한 문서는 아니다.

## 1. 검토 결론

수신·저장 분리, 제한된 Queue, 장애 상태 전달 및 복구 경로 유지에는 동의합니다. 다만 제안은 기존 서버의 일부 수정이 아니라 데이터 보존 정책, 서버 실행 환경, DB 구성을 함께 변경하는 내용입니다.

현재 운영 구조와 달라지는 사항을 먼저 합의한 뒤 필요한 부분부터 구현하고자 합니다. 문서의 '최종본' 표기와 별개로 아래 미확정 사항에 대한 회신을 요청합니다.

## 2. 현재 구조와 제안의 차이

| 항목 | 현재 프로젝트 | 전달받은 제안 |
| --- | --- | --- |
| Raspberry Pi | SQLite 1차 저장 및 미전송 데이터 동기화 | 메모리 Queue 기반 실시간 Gateway |
| 최종 서버 | Ubuntu VM | Gateway 문서상 WSL Final Server |
| 최종 DB | MariaDB | SQLite `edge_vision.db` |
| Vision 전달 확인 | DB 저장 후 메시지별 ACK | 메시지별 ACK 없음 |
| 장애 중 데이터 | Relay에 저장된 미전송 데이터를 복구 후 재전송 | 미처리 Vision 폐기, backlog 보관하지 않음 |
| 복구 후 처리 | 미전송 데이터 동기화 | 새로운 Vision부터 처리 |
| 센서 경로 | Arduino 데이터도 수신·저장·동기화 | 처리 범위가 명시되지 않음 |
| 상태 기록 | 기존 로그 | Control 및 `system_events` 추가 |

새 문서의 'Relay Server'는 최종 저장 서버를 의미하지만, 현재 프로젝트의 `relay_server`는 Pi 중계 서버입니다. 이후 문서에서는 'Pi Gateway'와 '최종 서버'로 구분해 주십시오.

## 3. 수용 가능한 개선 방향

- 수신과 DB 저장을 분리하고, 네트워크 대기 중 공용 DB 잠금을 유지하지 않는 구조
- 유한한 Queue와 명시적인 포화 처리 정책
- 처리량, Queue 깊이, 저장 지연, 폐기 건수의 확인
- 데이터 처리가 PAUSED여도 Control·연결 관리·복구 판단은 계속 실행
- 재연결 직후 현재 처리 가능 상태를 동기화
- 한 소켓의 수신 담당을 하나로 두고, 송신 시 헤더와 본문 전체를 직렬화
- 관찰된 연결 단절과 추정한 장비·네트워크 원인을 구분
- DB 장애 시 별도 로그로 오류 기록

이 개선들은 기존 Ubuntu·MariaDB 구성에서도 적용할 수 있습니다.

## 4. 데이터 유실 정책을 먼저 확정해야 합니다

기존 정책은 Relay SQLite에 저장된 Vision을 미전송 상태로 보관하고, 최종 서버 저장 확인 후 전송 완료로 처리하는 것입니다.

제안은 장애 시 Queue와 미처리 Vision을 폐기하며 개별 저장 완료를 확인하지 않습니다. TCP 전송 성공만으로 최종 DB 저장 완료가 보장되지는 않습니다. 수신 후 DB 저장 전에 프로세스가 종료되는 경우에도 데이터가 유실될 수 있습니다.

따라서 다음 사항은 성능 개선이 아니라 별도의 요구사항 변경으로 합의해야 합니다.

- 장애 및 복구 과정에서 Vision 유실을 허용하는가?
- 정상 운용 중 Queue 포화나 종료 시에도 미저장 Vision 폐기를 허용하는가?
- 손실 건수의 정확한 파악이 필요한가, 관측 가능한 폐기 건수와 장애 구간 기록으로 충분한가?

Stop-and-Wait가 전송률을 제한할 수 있다는 설명에는 동의합니다. 다만 실제 병목 정도는 측정값으로 확인해야 하며, Stop-and-Wait 개선과 모든 저장 확인 제거는 동일한 결정이 아닙니다. 저장 보장이 필요하면 비동기 또는 묶음 확인 같은 대안도 목적에 맞춰 검토할 수 있습니다. 현 단계에서 해당 대안을 추가 구현하자는 요청은 아닙니다.

## 5. 서버 환경과 센서 경로

서버 측 기본 제안은 기존 Ubuntu VM·MariaDB·Metabase 연결을 유지하는 것입니다. WSL 사용을 최소화한다는 기존 운영 방향도 있습니다.

연속 송신이나 Control 도입을 위해 최종 서버를 WSL로, DB를 SQLite로 바꿔야 하는 필수 이유는 현재 문서에서 확인되지 않습니다. WSL·SQLite가 개발 예시인지, 실제 교체 요구인지 명확히 해 주십시오. 교체 요구라면 기존 구성으로 해결할 수 없는 이유와 Metabase 연결 변경 방안이 필요합니다.

Arduino 센서는 현재 같은 Pi 서버를 사용합니다. Vision PAUSE가 센서 수신·저장까지 정지시키거나 센서 미전송 데이터를 폐기해서는 안 된다는 방향을 제안합니다. Vision 전용 정책인지 전체 데이터 정책인지 범위를 명시해 주십시오.

## 6. 장애 기록의 해석 범위

`system_events`를 이용한 장애 구간 추적은 유용합니다. 다만 현재 명세만으로 데이터 공백의 모든 원인을 확정할 수 있다는 표현은 조정이 필요합니다.

- 연결 단절은 확인할 수 있지만, 장비 전원 OFF·프로세스 종료·네트워크 장애를 항상 구별할 수는 없습니다.
- 연결이 살아 있어도 카메라 획득이나 추론이 정지할 수 있습니다.
- 장애 이벤트가 없다는 이유만으로 '차량이 없었다'고 판단할 수 없습니다. 무탐지와 탐지 실패도 구별해야 합니다.
- DB 장애 시 이벤트가 파일에만 기록된다면 DB 조회만으로 모든 장애 구간을 확인할 수는 없습니다.
- 최종 서버 자체가 종료된 동안의 사건은 재시작 기록만으로 정확한 발생 시각까지 복원할 수 없습니다.

따라서 보장 범위는 우선 **관측·기록된 장애와 복구 상태를 확인할 수 있음**으로 정의해 주십시오. 정상 처리 중 무탐지까지 구분하는 것이 필수라면 카메라·추론 진행 정보 또는 최소 프레임 상태가 별도로 필요합니다. Heartbeat 역시 연결 생존과 실제 추론 진행을 구분해서 정의해야 합니다.

## 7. Control 및 복구 규격 보완

다음은 구현 전에 공통 규격으로 확정해야 합니다.

1. **명칭 통일:** `jetson_connection_lost/restored`와 `jetson_disconnected/reconnected` 등 두 문서의 reason을 통일합니다.
2. **최초 상태 동기화:** READY/PAUSED의 실제 JSON 형식과 확인 제한시간을 정합니다. 상태 확인 전에는 데이터 처리를 시작하지 않는 기준이 필요합니다.
3. **복수 장애:** DB 장애와 Queue 장애가 겹쳤을 때 하나의 복구 이벤트로 전체 PAUSE가 해제되지 않도록 합니다. '개별 원인 복구'와 '전체 처리 가능'의 의미를 구분해야 합니다.
4. **연결 세션:** 이전 연결의 Control이 새 연결 상태를 변경하지 않도록 세션 구분 및 중복 Control 처리 기준을 정합니다.
5. **장애 감지 시간:** 재접속 간격, 연결·송신 대기 제한시간, keepalive 또는 health 메시지 주기와 실패 기준을 정합니다.
6. **Queue 정책:** 최대 크기, 포화 시 기존/신규 중 폐기 대상, PAUSE 전환 조건과 재개 조건을 정합니다. Queue를 비웠다는 사실만으로 처리 성능이 회복됐다고 판단하지 않습니다.
7. **Control 전달:** Data/Control을 같은 TCP 연결로 보낼 때 Data 송신이 막혀 Control도 무기한 기다리지 않도록 송신 대기와 실패 처리 기준을 정합니다.
8. **프레임 검증:** 최대 payload 크기와 잘못된 JSON·지원하지 않는 type의 처리 기준을 유지 또는 확정합니다.

## 8. '새 데이터부터 재개'의 정확한 의미

메모리 Queue를 비워도 TCP 송수신 버퍼, 이미 꺼낸 작업, 진행 중인 DB 저장에는 이전 데이터가 남을 수 있습니다.

복구 후 과거 데이터의 저장을 엄격히 금지할 것인지, 이미 처리 중인 일부 메시지는 허용할 것인지 정해야 합니다. 엄격한 정책이라면 세션 또는 처리 세대 구분, 폐기 경계 등 구현 가능한 기준이 필요합니다.

Vision `timestamp_ms`는 기존 합의대로 **카메라 프레임 획득 시각**으로 유지해 주십시오. '획득/Detection 기준'처럼 두 의미를 혼용하지 않습니다. 장치 간 이벤트 시각 비교를 위해 시계 동기화도 필요하며, timeout 측정은 시스템 시각 변경에 영향을 받지 않는 기준으로 구현해야 합니다.

## 9. 요청하는 회신과 진행 순서

우선 아래 사항에 답변해 주십시오.

1. WSL·SQLite는 예시입니까, 기존 Ubuntu·MariaDB 교체 요구입니까?
2. 제안한 Vision 정책은 장애·과부하·종료 시 미저장 데이터 유실을 허용하는 정책이 맞습니까?
3. Arduino 센서는 이번 정책 변경에서 제외하고 기존 경로를 유지할 수 있습니까?
4. Control 공통 명칭, READY 형식, Queue·timeout·복구 기준을 양측에서 확정할 수 있습니까?
5. 데이터 공백 설명은 '관측된 장애 기록' 수준입니까, 정상 무탐지와 수집 중단까지 구분하는 수준입니까?

회신 후 **운영 환경 및 보존 정책 합의 → 최소 통신·상태 규격 확정 → 필요한 서버 변경 → 실제 장치 통신 확인** 순서로 진행하고자 합니다.

그 전까지 기존 ACK·미전송 데이터 보관 정책, DB 및 센서 경로를 임의로 제거하지 않습니다. 이번 회신의 목적은 새 설계를 거절하는 것이 아니라, 성능 개선과 서비스 정책 변경을 명확히 구분하여 양측이 같은 요구사항으로 구현하는 것입니다.

# Vision Gateway / Final Server 추가 회신

작성일: 2026-10-01

## 1. 검토 결과

회신 확인했습니다. Jetson 이전 및 TensorRT 적용 후 Vision 생성 처리량이 증가했고, 기존 전송 경로에서 Queue 포화가 관측됐다는 변경 배경을 이해했습니다.

이번 작업은 Jetson의 추론·탐지 기능을 다시 설계하는 작업이 아니라, 증가한 데이터 생성량에 맞춰 통신·Queue·저장 처리를 개선하는 작업으로 정리하겠습니다.

아래 방향으로 진행하되, 실제 연결에 필요한 잔여 규격을 먼저 맞추겠습니다. 이 문서는 구현·배포 완료를 의미하지 않습니다.

## 2. 적용 방향

- Final Server는 기존 Ubuntu VM·MariaDB 환경을 유지합니다. Metabase의 기존 MariaDB 연결도 유지합니다.
- Arduino 센서의 수신·저장·동기화 정책은 유지합니다. Vision PAUSE나 Queue 폐기가 센서 경로에 영향을 주지 않도록 합니다.
- Jetson의 카메라·TensorRT 추론·탐지·객체별 Vision JSON 생성 로직은 유지합니다.
- Vision은 메시지별 application ACK 없이 연속 송신하는 방향으로 변경합니다.
- Vision은 실시간성을 우선하며, 장애·과부하·종료 과정에서 최종 저장 전 데이터가 유실될 수 있음을 정책에 반영합니다. TCP 전송 완료를 DB 저장 완료로 해석하지 않습니다.
- PAUSE 시 대기 중인 Vision을 폐기하고, 복구 후 의도적인 backlog 재전송은 하지 않습니다. 이미 DB 처리가 시작된 메시지는 저장 완료될 수 있습니다.
- 장애 이벤트는 실제 관측한 상태만 기록하며, 데이터 부재를 차량 부재나 특정 장비 고장으로 단정하지 않습니다.
- 복수 장애 원인을 관리하고 모든 차단 조건이 해소된 경우에만 재개합니다.

Vision `message_id`와 카메라 프레임 획득 시각인 `timestamp_ms`는 그대로 유지합니다. Vision JSON에 별도 generation ID를 추가하도록 요구하지 않습니다.

## 3. 구현 시 확인할 사항

### 병목 개선 범위

Queue 포화는 처리량 불균형의 근거로 받아들입니다. 다만 메시지별 ACK 대기뿐 아니라 Gateway의 공용 잠금, 최종 서버의 저장 지연과 소켓 대기도 함께 확인하겠습니다.

서버 측에서는 수신·저장 분리와 네트워크 대기 중 공용 DB 잠금 유지 문제를 함께 개선하겠습니다. ACK 제거만으로 모든 병목이 해소됐다고 판단하지 않고 실제 메시지 처리량과 Queue 상태로 확인하겠습니다.

### Jetson 변경 범위

'Jetson Vision 생성 로직 유지'에 동의합니다. 다만 ACK 제거와 Control 도입은 양측 통신 동작이 일치해야 하므로, Jetson의 통신 부분이 이미 새 방식으로 구현됐는지 확인이 필요합니다.

기존 ACK 대기 방식의 Jetson과 ACK를 반환하지 않는 Gateway를 혼용하지 않도록 적용 순서도 맞추겠습니다.

### 복구 경계

메모리 Queue를 비워도 전송 중이거나 TCP 버퍼에 남은 메시지가 일부 도착할 수 있습니다. 엄격한 transaction boundary를 요구하지 않는다는 회신에 따라, 이러한 메시지도 일부 처리될 수 있는 정책인지 확인 부탁드립니다.

의도적인 과거 backlog 재전송은 하지 않되, 모든 이전 메시지를 한 건도 남김없이 차단하는 기능은 이번 범위에서 제외하는 것으로 이해하고 있습니다.

## 4. 요청 자료

이미 구현하거나 측정한 내용이 있다면 새로 작성하기보다 해당 코드·설정·로그를 공유해 주시면 됩니다.

1. **Jetson 통신 구현 상태**
   - ACK 없는 연속 송신, Control 수신, PAUSE/RESUME, 재연결의 구현 여부
   - PAUSE 중 Vision 생성·Network Queue 적재·폐기 동작
   - 최초 연결 후 처리 가능 상태를 확인하기 전 송신 여부

2. **실제 Control 규격**
   - 최초 `action=resume`, `reason=server_ready`를 포함한 JSON 예시
   - 현재 사용하는 action·reason 전체 목록과 의미
   - `resume`이 개별 장애 해제를 뜻하는지, 송신 노드의 전체 처리 가능 상태를 뜻하는지
   - 재접속 시 현재 상태 동기화 방식

3. **현재 설정값**
   - 최대 JSON payload 크기
   - Queue 용량·단위, 포화 시 기존/신규 데이터 폐기 방식
   - 연결·송신·최초 상태 확인 timeout과 재접속 간격
   - 사용 중인 keepalive 또는 health 메시지 규칙

   숫자를 아키텍처에 영구 고정할 필요는 없지만, 연동 시 사용할 초기 설정은 공유해야 합니다. 각 구간의 설정은 목적에 맞게 정하되 서로 충돌하지 않도록 맞추겠습니다.

4. **실제 Vision 메시지 처리량**
   - 생성 메시지 수/초, 송신 메시지 수/초
   - Queue 깊이와 overflow/drop 건수
   - 가능하면 기존 방식과 연속 송신 방식의 비교 결과

   객체별 전송이므로 서버 용량 판단에는 FPS와 함께 메시지 수/초가 필요합니다.

## 5. 다음 진행

요청 자료를 바탕으로 공통 통신 규격과 초기 설정을 확정한 뒤, Pi Gateway 및 Ubuntu Final Server를 수정하고 실제 장치로 검증하겠습니다.

검증에서는 Vision 연속 수신·저장, 장애 시 PAUSE, 재접속 및 상태 동기화, 복수 장애 해제, Queue 제한과 폐기 기록을 확인합니다. 동시에 Vision 장애가 Arduino 센서 수신·저장·동기화를 중단시키지 않는지도 확인하겠습니다.

기존 테이블과 저장 데이터의 삭제는 이번 작업에 포함하지 않습니다. 운영 전환 전 기존 Vision 미전송 데이터의 처리와 새 통신 방식 적용 시점을 양측이 맞추겠습니다.

# Vision 기능 방향 정리 및 시야·성능 개선 검토 요청

작성일: 2026-09-28

상태: 서버 측 방향 정리 및 Vision 측 협의 요청. 이 문서는 코드 변경이나 기능 삭제 완료를 의미하지 않는다.

## 1. 현재 상황과 판단

현재 화면은 나무 틈새로 도로 일부만 보이며, 주로 한쪽 방향의 차량을 관측한다. 사용자 관찰에 따르면 동시에 보이는 차량은 많아야 약 0~3대이고, 낮은 처리 FPS 때문에 차량 위치가 프레임 사이에서 크게 이동하는 모습이 나타난다. 기존 Tracking·기준선 통과 방식의 `traffic_count`는 0이 지속되는 상황이 보고됐다.

현재 시야·가림·처리 성능 조건에서는 수집값을 실제 통과 차량 대수나 시간대별 도로 혼잡도를 나타내는 신뢰할 만한 지표로 사용하기 어렵다고 판단한다. 이는 작은 화면에서는 언제나 측정이 불가능하다는 뜻이 아니라, 현재 조건과 확인된 자료로는 그러한 해석을 뒷받침하기 어렵다는 뜻이다.

실제 추론 FPS, 차량별 관측 횟수, Tracking 유지율, 기준선 판정 실패 원인은 아직 수치로 확인되지 않았다. 따라서 `traffic_count = 0`을 차량이 없었다는 의미로 해석하거나 특정 원인으로 단정하지 않는다.

## 2. 논의한 대안과 한계

| 방식 | 측정하려는 값 | 현재 조건에서의 한계 |
| --- | --- | --- |
| Tracking + 기준선 통과 | 구간별 통과 차량 수 | 같은 차량의 연속 관측과 ID 유지가 필요하며, 가림·낮은 FPS로 누락될 수 있음 |
| 5초 평균 탐지 차량 수 | 처리 프레임에서 평균적으로 탐지된 차량 수 | 실제 통과 대수가 아니며, 좁은 시야와 탐지 누락의 영향을 받음 |
| 차량 관측 프레임 비율 | 유효 프레임 중 차량이 탐지된 프레임 비율 | 정차한 한 대도 높은 값을 만들 수 있어 통과량·혼잡도를 직접 의미하지 않음 |

같은 차량을 여러 프레임에서 관측한 횟수를 합산해 누적 차량 대수로 표시하지 않는다. 평균이나 관측 비율로 바꾸더라도 프레임 사이에 지나가거나 가려진 차량을 복원할 수는 없다.

따라서 지금은 `traffic_state` 메시지와 테이블을 새로 추가하는 작업도 보류한다.

## 3. 당분간 유지할 프로젝트 방향

프로젝트의 중심을 **차량·환경 데이터 수집 및 원격 모니터링**으로 둔다.

- Vision: 기존 객체별 `vision` JSON으로 탐지 시각, 차종, confidence, bbox, frame_id 등을 계속 전달한다.
- Arduino: 기존 환경 센서 데이터를 계속 수집한다.
- 서버: 기존 수신·저장·동기화 흐름으로 데이터를 축적한다.
- 시각화: 차량 탐지 이력과 센서값의 시간별 변화를 보여준다.

기존 `vision` 메시지 형식과 4바이트 big-endian 길이 헤더, ACK, message_id 재전송 규칙은 유지한다.

탐지 이력은 동일 차량의 반복 탐지를 포함한다. 표시 명칭은 '차량 탐지 이력', '탐지 건수' 등으로 사용하고, 이를 '통과 차량 대수', '누적 교통량', '혼잡도'로 표시하지 않는다. 탐지 건수 또한 처리 FPS와 탐지 성능의 영향을 받으므로 실제 교통량 비교 지표로 사용하지 않는다.

현재 객체가 없는 프레임은 `vision` 메시지를 보내지 않으므로, 수신 데이터가 없다는 사실만으로 차량 부재와 장치·통신 장애를 구별할 수 없다.

## 4. 기존 traffic_count 처리 방침

`traffic_count` 기반 교통량 해석과 누적 교통량 그래프의 활용은 보류한다. 기존 코드, 테이블, 저장 데이터는 이번 문서 작업으로 삭제하거나 변경하지 않는다.

Vision 측의 `traffic_count` 송신 및 Tracking 기능을 계속 켜둘지, 설정으로 일시 중지할지는 회신 후 협의한다. 송신 중지나 성능 개선 작업을 하더라도 기존 `vision` 데이터 송수신은 유지하는 것을 기준으로 한다.

시야·성능 개선 후 실제 관측 결과를 확인하고 통과량 기능의 재개 여부를 판단한다.

## 5. Vision 측 요청사항

우선 현재 장비와 설치 조건에서 아래 개선이 가능한지 검토해 달라. 대규모 신규 기능 구현보다 가능한 조정과 한계 파악을 우선한다.

1. **시야 개선 가능 여부**
   - 카메라 위치·높이·각도를 바꿔 나무 가림을 줄일 수 있는가?
   - 차량이 더 오래, 연속적으로 보이는 도로 구간을 확보할 수 있는가?
   - 시야를 넓히면서 원거리 차량이 너무 작아져 탐지가 어려워지는 문제는 없는가?
2. **실제 처리 성능과 개선 가능 여부**
   - 카메라 입력 FPS와 실제 추론 FPS, 프레임 간격은 각각 어느 정도인가?
   - 추론, 전처리·후처리, 화면 표시, TCP 전송·ACK 대기 중 어느 부분이 처리 속도를 제한하는가?
   - 기존 장비에서 모델·입력 크기·처리 흐름 조정으로 개선할 여지가 있는가? 속도 개선 시 탐지 정확도 영향도 함께 확인해 달라.
3. **짧은 실제 영상 기준 확인**
   - 사람이 볼 수 있는 차량이 추론 결과에도 나타나는지, 차량 한 대가 몇 개 프레임에서 관측되는지 확인해 달라.
   - 기존 통과량이 0인 원인이 탐지 누락, ID 변경, 기준선 위치, 교차 판정 중 어디에 있는지 확인 가능한 범위에서 알려 달라.

## 6. 요청하는 회신

- 현재 시야·FPS에서 가능한 것과 어려운 것
- 시야 및 성능 개선안, 적용 가능 여부와 예상 제약
- 가능하면 개선 전후 실제 FPS와 차량 관측 사례
- 기존 `vision` 송수신을 유지하면서 `traffic_count`를 보류하는 방법

개선이 어렵다면 현재 하드웨어의 한계를 인정하고 차량 탐지 이력과 센서 데이터 모니터링을 최종 범위로 유지한다. 개선이 가능하다면 결과를 먼저 확인한 뒤 교통량·교통 상태 분석의 재도입과 JSON·DB 변경을 별도로 합의한다.
